# Протокол BLE vabuGEOde — версия 2

Логика, когда что передаётся, — в [gadget-logic.md](gadget-logic.md).

Изменения v2 относительно v1: маячок в рекламе; режимы питания CAMP/MOVING/ECONOMY/CRITICAL;
байт тревог в STATUS; настройки GPS и радио в INFO; сообщение ALERT; команды SESSION, BYE,
SET_GPS_MODE, SET_RADIO, ACK_ALERT; бит причины подмены 6 (время).
Дополнения v2 (обратно совместимы): журнал гаджета — сообщение LOG, команды SYNC_LOG, SET_DEBUG.

Общий для прошивки (`firmware/`) и приложения (`android/`). Любое изменение формата —
сначала здесь, потом в обоих местах, потом обновить тест-векторы `docs/protocol_vectors.json`.

## GATT

| Что | UUID | Свойства |
|---|---|---|
| Сервис | `e0f30001-5642-4744-8a1e-76616275676f` | |
| Status | `e0f30002-5642-4744-8a1e-76616275676f` | notify, read |
| Command | `e0f30003-5642-4744-8a1e-76616275676f` | write (с ответом) |
| Event | `e0f30004-5642-4744-8a1e-76616275676f` | notify |

`5642 4744` = «VBGD», `76616275676f` = «vabugo».

- Инициатор подключения — телефон. Устройство только рекламируется (см. «Маячок»), реклама подключаемая.
- После подключения телефон **обязательно** запрашивает MTU 247. Самый длинный пакет — 99 байт (SATS),
  при MTU 23 пакеты не пролезут.
- Сопряжение (bonding) обязательно: команды от несопряжённого телефона устройство отклоняет.

## Общие правила

- Порядок байт — **little-endian**. Чисел с плавающей точкой нет, только целые с масштабом.
- Байт 0 — версия протокола (`2`), байт 1 — тип сообщения или команды.
- Устройство отвечает на неизвестную версию событием `ACK` с `result = 3`.
- «Нет данных» для знаковых 16-битных полей — `0x8000` (−32768), для `hdop` — `255`.
- Время — Unix-секунды UTC (`u32`).
- Координаты — градусы × 10⁷ (`i32`). `0, 0` = нет координат.

## Перечисления

| mode | | fix | | src | | sat system | |
|---|---|---|---|---|---|---|---|
| 0 | CAMP (стоянка) | 0 | OFF | 0 | NONE | 0 | GPS |
| 1 | MOVING (в пути) | 1 | SEARCHING | 1 | GPS | 1 | BeiDou |
| 2 | ECONOMY (экономия) | 2 | FIX_2D | 2 | PDR | 2 | ГЛОНАСС |
| 3 | CRITICAL (критический заряд) | 3 | FIX_3D | | | 3 | Galileo |

`spoof_mask` — биты причин подмены (ТЗ, раздел 7): 0 чёрный список, 1 расхождение с телефоном,
2 невозможный скачок, 3 одинаковый SNR, 4 барометр против GPS, 5 шаги против GPS,
6 время GPS расходится с часами DS1302, 7 ожидание подтверждения восстановления после подмены.
После обнаруженной подмены прошивка требует не менее 10 с чистых фиксов, минимум три
различных момента времени; перерыв между ними более 3 с начинает подтверждение заново.

`alerts` — биты активных тревог: 0 подмена GPS, 1 низкий заряд (< 15 %), 2 критический заряд (< 5 %), 3 ошибка SD.

`gps_mode`: 0 «всегда» (в пути GPS включён), 1 «импульсы».

Типы меток: 0 метка (кнопка A), 1 зашли, 2 нашли, 3 охрана, 4 интересно, 5 хлопушка (SYNC), 6 текст.

## Маячок (реклама)

Реклама подключаемая (`ADV_IND`). Данные рекламы (31 байт):

| Поле AD | Длина | Содержимое |
|---|---|---|
| Flags | 3 | `02 01 06` |
| Manufacturer Specific | 2 + 2 + 18 | company id `0xFFFF` (тестовый, LE: `FF FF`), затем 18 байт сводки |

Ответ на сканирование (scan response): полный UUID сервиса (18 байт) + имя `vabuGEOde` (11 байт).
Телефон фильтрует маячки по company id `0xFFFF` и байту-метке `0x56`.

Сводка, 18 байт:

| Смещение | Тип | Поле |
|---|---|---|
| 0 | u8 | ver = 2 |
| 1 | u8 | метка = 0x56 («V») |
| 2 | u8 | mode |
| 3 | u8 | flags: бит 0 запись, 1 есть фикс, 2 подмена, 3 время проверено, 4 окно открыто, 5 SD в порядке |
| 4 | u8 | alerts |
| 5 | i16 | temp_corr ×100 (`0x8000` — нет) |
| 7 | u8 | batt_pct |
| 8 | u8 | sats_used |
| 9 | u16 | pressure ×10 гПа (0 — нет) |
| 11 | u32 | время последней записи трека, Unix-с — есть ли новое для синхронизации |
| 15 | u16 | номер похода: младшие 16 бит hike_start |
| 17 | u8 | счётчик маячков (по кругу) |

Координат в маячке нет намеренно (gadget-logic.md, раздел 2).

## Порядок при подключении

1. Телефон: MTU 247, подписка на Status и Event.
2. `SET_TIME` (время телефона), `PHONE_POS` (если есть геолокация), `BLACKLIST`.
3. `GET_INFO` → `INFO`.
4. `SYNC_TRACK(последняя известная точка)` → поток `POINT` → `SYNC_DONE`.
5. `SYNC_MARKS(...)` → поток `MARK` → `SYNC_DONE`.
5а. `SET_DEBUG(настройка приложения)`, `SYNC_LOG(последний известный seq)` → поток `LOG` → `SYNC_DONE`.
6. `SESSION 1` (живой) — устройство шлёт `STATUS` раз в секунду, `SATS` раз в 5 с, новые `POINT` и `MARK` сразу.
7. Приложение свернули: `SESSION 0` через 30 с, `BYE` через 2 мин. Молчание телефона 60 с — устройство рвёт связь само.


## Управление походами (прошивка 0.1.13, приложение 0.9.5)

- `0x15 NEW_HIKE`: u32 ожидаемый текущий `hike_start`. Сбрасывает буфер старого похода на SD,
  закрывает его и начинает новый с уникальным ID. При несовпадении ID, активной выгрузке или
  недоступной SD возвращает BUSY, не начиная новый поход.
- `0x16 DELETE_HIKE`: u32 `hike_start` удаляемого архива. Текущий поход и нулевой ID удалять нельзя.
  Удаляются `/tracks/*.csv`, `/tracks/*.bin`, `/marks/*.csv`, `/marks/*.bin` только выбранного ID.
  Отсутствующие файлы — успешный повтор удаления; ошибки удаления не считаются успехом.
- Ответ `0x0A HIKE_RESULT`: после заголовка u8 код команды, u8 результат ACK, u32 ID из запроса.
  Длина пакета 8 байт. Для NEW_HIKE затем приходит INFO с новым текущим ID.
  В случае ошибки декодирования остаётся обычный ACK.

Приложение сопоставляет ответ с командой и ID и ждёт до 15 секунд. Без положительного
подтверждения SD-удаления локальную копию не удаляет. При потере ответа следует переподключиться:
повтор удаления безопасен; NEW_HIKE со старым ожидаемым ID не создаёт ещё один поход.

## Приблизительный маршрут и компас (прошивка 0.1.14, приложение 0.9.6)

Историческое поведение 0.1.14. В 0.1.15 источник направления для PDR заменён автоматическим
инерциальным алгоритмом, описанным ниже; калибровка магнитного компаса остаётся дополнительной.

- `0x17 PDR_SETTINGS`: `u16 stride_cm` (30…150), `i16 heading_offset10` (−1800…1800),
  `u8 inverted` (0/1), всего 7 байт с заголовком. Ответ — обычный ACK. Параметры хранятся в NVS.
- `CALIB_COMPASS 1` начинает сбор QMC5883P (0x2C, ID 0x80); шаги временно не считаются,
  глубокий сон запрещён. `CALIB_COMPASS 0` сохраняет смещения/масштабы трёх осей и положение
  акселерометра только после ≥20 с, ≥100 отсчётов и достаточного размаха по каждой оси.
  Неполная калибровка даёт BAD_ARGS и продолжает сбор; через 180 с сбор отменяется.
  Успешная калибровка хранится в NVS, переживает сон и выключение. После команды приходит INFO.
- INFO, проверка id=4: code=13 — сбор калибровки, code=3 — нужна калибровка,
  code=0 — сохранена. Старые QMC5883L/HMC5883L только обнаруживаются; их калибровка не реализована.
- STATUS.heading: направление компаса ×10°, `65535` — неизвестно. STATUS.course при src=PDR
  также содержит направление оценки, при src=GPS — курс GPS. Размер пакетов не изменился.
- PDR начинается только от принятого проверкой GPS либо PHONE_POS с точностью 1…1000 м,
  вне чёрного списка. Телефон передаёт позицию возрастом ≤30 с; кнопка «Начало от телефона»
  дополнительно делает разовый запрос сетевой позиции с ожиданием до 10 с. Если начало уже есть,
  PHONE_POS его не переносит. Начало теряется при холодном включении, паузе и новом походе;
  после них нужен новый GPS/PHONE_POS. При глубоком сне начало и счисление сохраняются в RTC.
- Для каждого шага используются заданная длина и последнее пригодное направление (не старше 2 с).
  При сильном наклоне/ускорении, магнитной помехе или отсутствии отсчётов направление отвергается.
  Если при этом появились шаги, счисление прерывается до новой привязки, чтобы не рисовать
  неизвестное направление. Оценка не имеет полной компенсации наклона/гироскопа: плата компаса
  должна лежать горизонтально, передняя сторона корпуса постоянно направлена по ходу движения.
- В POINT `src=2` означает независимое счисление, даже при `spoof=1`: флаг относится к GPS,
  ложные GPS-координаты остаются в `spoof_lat/lon`. Такие координаты не используются для PDR.
  src=0/3 и недостоверные GPS по-прежнему разрывают линию. Расстояние по шагам не прибавляется
  второй раз как хорда GPS после возвращения сигнала.
- Приложение исправляет отображение законченного PDR-участка: при двух GPS-привязках распределяет
  ошибку конца пропорционально шагам, сохраняя начало; при начале от телефона переносит весь
  участок к первому GPS. Коррекция ограничена 2 км, при двух GPS — также max(100 м, 1,5 ×
  число шагов × 0,75 м). Большие несоответствия, разрывы >120 с, сброс шагов и подмена не соединяются.
  Сырые записи на SD и в базе не переписываются. Это оценка; точность в процентах не гарантируется.

## Автоматическое направление ходьбы (прошивка 0.1.15, приложение 0.9.7)

Размеры STATUS/POINT/INFO и команды не меняются. В INFO добавлена проверка id=10:

| code | Состояние |
|---|---|
| 0 | Привязка к GPS есть, ось ходьбы пригодна |
| 14 | Нужно пройти с достоверным GPS |
| 15 | Нужно автоматическое измерение смещения гироскопа в короткий момент покоя |
| 16 | Ось ходьбы пока ненадёжна / ожидается движение |
| 17 | Более 20 мин без уточнения по GPS, накапливается дрейф |

MPU6050 во время бодрствования читает ускорения ±2 g и гироскоп ±500 °/с одним пакетом 14 байт
с частотой около 25 Гц. Ориентация переносит ускорения из корпуса в неподвижную систему;
низкочастотная гравитация корректирует крен/тангаж. Ось ходьбы — главная ось горизонтальной
ковариации окна из 80 отсчётов, при ≥3 шагах и достаточной амплитуде/анизотропии.
Привязка к северу обучается только в ветке GPS, уже прошедшего фильтрацию качества/подмены:
перемещение ≥10 м, ≥6 шагов, возраст базы ≤20 с, скорость ≤3,5 м/с и расстояние ≤2 м на шаг.
Корпус не обязан смотреть по ходу движения. Подмена, PHONE_POS и одно вращение на месте
не обучают направление. Магнитометр и его взаимная установка с MPU для этого алгоритма не нужны.

Неоднозначность оси на 180° выбирается по предыдущему направлению. Без промежуточных шагов
точный разворот на месте может быть не распознан. Изменение рисунка движений руки также может
быть принято за изменение оси ходьбы. Это эвристика для приблизительного пунктира, не точная
инерциальная навигация; реальная точность и расход на собранном трекере ещё не измерены.

Последняя пригодная ось используется не дольше 10 с. Пропуск IMU >1 с, сброс счётчика шагов или
насыщение гироскопа сбрасывают ориентацию/обучение; неизвестные перемещения не дорисовываются.
Короткие задержки SD проходят с интегрированием последней угловой скорости как приближением.
Смещение гироскопа автоматически измеряется по спокойным отсчётам (≥2 с, малая вариация)
и сохраняется в RTC между снами. Ориентация во сне не наблюдается, поэтому после сна требуется
новая GPS-привязка направления. В автоматическом сне гироскоп выключен. Во время коротких
остановок после участка PDR без GPS допускается до 5 мин бодрствования при наличии позиции и записи;
критический заряд отменяет удержание. Обновление положения, запись PDR и коррекция в приложении
остаются как в 0.1.14, но направление теперь берётся из инерциального алгоритма. STATUS.heading
по-прежнему относится к отдельному магнитному компасу; направление PDR — в course/POINT.heading.
