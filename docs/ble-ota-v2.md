# BLE OTA V2: реализация и условия приёмки

12.11.2026. Владелец разрешил реализацию простого сценария целиком. Исходники:
**ESP32 0.1.32 / Android 0.10.9 (32)**. Код, подписанный образ в APK и USB-bootstrap
подготовлены; **на V2 функция ещё не испытана**. Это не готовность к продаже.
[Программные проверки](software-evidence/2026-11-12/ble-ota-implementation.md),
[основной список OTA1–OTA7](software-roadmap.md#ble-ota-v2),
[скачивание и версии](STATUS.md). Прежний [анализ](archive/ble-ota-v2-analysis-20261112.md)
и [аудит 0.1.25](software-evidence/2026-11-12/ble-ota-build-audit.md) — история.

## Согласованный сценарий и ограничения

1. Один раз установить USB-комплект V2 с новой разметкой и приёмником. Один APK
   не добавит OTA в уже установленную старую прошивку. V1 не поддерживается.
2. APK содержит необязательные `assets/firmware/app.bin`, `manifest.bin`, `public.der`.
   В 0.10.9 включён реальный V2 Slider 0.1.32. Нет загрузки из интернета во время передачи.
   Следующий APK может сохранить этот образ или не содержать его; обновлять прибор
   при каждом выпуске приложения не требуется.
3. Подключить прибор, завершить поход и выгрузку, открыть «Настройки → Прошивка прибора».
   Проверка сверяет фактические сведения прибора и образ APK. Обновление начинается
   только после отдельного подтверждения пользователя.
4. Приложение остаётся на экране. Один GATT, существующее сопряжение/шифрование,
   MTU не менее 247. После обрыва/сворачивания — прерывание, проверка состояния,
   новая передача с нуля по явному действию. Возобновления с середины и фонового сервиса нет.
5. После проверки и выбора слота приложение запрашивает перезапуск. Прибор отвечает
   до reset; LinkManager переподключается. **100% передачи не означает успех**:
   нужны версия, SHA-256 и подтверждённый первый запуск от самого прибора.
   До испытания ON/EN сохраняется запасной ручной запуск и кнопка «Проверить».

## Flash и однократная USB-подготовка

Проект настроен на S3FH4R2, 4 МиБ flash / 2 МиБ PSRAM. Это конфигурация, не измерение
экземпляра. Скрипт USB требует измеренные `flash_id` 4MB и ESP32-S3. Модель продукта
V2 и соответствие проводки **подтверждает оператор**, чип сам не определяет нашу плату.
Логические product model=1, wiring revision=2, power profile=Slider(1), layout=1,
основной BLE wire=2, OTA wire=1. Для другой проводки нужен отдельный совместимый профиль.

Рабочая `firmware/ota/partitions.csv`:

| Раздел | Адрес | Размер | Изменение |
|---|---:|---:|---|
| bootloader / таблица | 0x0 / 0x8000 | до NVS | USB, не OTA |
| nvs | 0x9000 | 0x5000 (20 КиБ) | адрес и размер сохранены |
| otadata | 0xE000 | 0x2000 | USB инициализирует выбор app0 |
| app0 | 0x10000 | 0x180000 (1,5 МиБ) | прежний 3 МиБ слот уменьшен |
| app1 | 0x190000 | 0x180000 (1,5 МиБ) | второй слот, прежний хвост app0 |
| spiffs | 0x310000 | 0xE0000 | сохранён |
| coredump | 0x3F0000 | 0x10000 | сохранён |

Лимит подписываемого app-only файла **0x140000 = 1 310 720 байт**: ещё 256 КиБ
резервируется внутри каждого слота. Свежие размеры и хеши — в свидетельствах проверки.
Ни размер, ни успешная сборка не подтверждают надёжность обновления.

USB-комплект включает bootloader, таблицу, boot_app0 и базовый приёмник **0.1.29**
(`s3_ota_bootstrap`: тот же новый код, отдельный номер базовой версии). Это позволяет
проверить реальный переход 0.1.29 → 0.1.32 из APK; это не старая историческая прошивка.
Скрипт `tools/prepare_ota_usb.py` из полного архива:

```sh
python3 -m pip install -r requirements.txt
python3 tools/prepare_ota_usb.py --port COM5 --backup /PRIVATE/v2-before-ota.bin --confirm-v2 --apply
```

`COM5` и путь заменить своими; для Linux возможен `/dev/ttyACM0`. Копия должна быть
НОВЫМ приватным файлом вне архива и git. Сначала на макете подтвердить питание ON при
reset и USB; использовать тестовую SD, отдельно скопировать её файлы. Скрипт не запускается
сам и в этой среде на приборе **не выполнялся**.

До записи: проверка контрольных сумм, типа/flash/security baseline, две одинаковые
полные копии flash 4 МиБ без запуска приложения между чтениями, проверка исходной
таблицы. Неожиданная разметка/защищённый чип — отказ, ручной аудит. Поддерживаются
прежний huge_app проекта и уже установленный layout1; произвольная плата не поддерживается.
Затем запись только 0x0/0x8000/0xE000/0x10000, **без erase-all/форматирования**.
Скрипт не меняет eFuse. После самопроверки USB-команда `ota provision` фиксирует явное
подтверждение модели/проводки в NVS; без него BEGIN запрещён.

NVS/settings/bonds, SPIFFS/coredump и внешняя SD не переносятся и не стираются.
В otadata прежний выбор стирается, app0 заменяется, старый хвост app0 становится app1:
прежний бинарник не сохраняется как rollback-образ. Сразу после USB есть **только одна
рабочая база**. Откат ко второму слоту появляется после первого принятого OTA.
Полная копия flash содержит приватные данные/bonds: не отправлять её в GitHub/логи.
Сохранность на настоящем контроллере SD/flash требует испытаний; адреса сами её не доказывают.

## Передача и безопасная активация

`ota_transfer.h` — переносимое ядро, `ota.cpp` — фактическая интеграция ESP-IDF;
`OtaProtocol.kt` / `OtaClient.kt` — формат и Android-клиент. Полный wire-контракт —
[protocol.md](protocol.md#ble-ota-v2-wire1).

- QUERY возвращает модель/проводку/питание/разметку/flash/слот, текущие версию/hash,
  состояние операции/boot, ключ и условия допуска. Обновление не определяется по кэшу INFO.
- BEGIN: отдельный ненулевой ID операции, фиксированный подписанный manifest.
  Проверки совместимости/подписи/версии/питания до `esp_ota_begin` и стирания.
- DATA: не более 224 байт, offset/CRC32. Только один пакет в работе, ответ после
  `esp_ota_write`; offset ответа — следующий ожидаемый байт. Повтор последнего
  пакета сверяется чтением flash и не записывается второй раз. Чужой ID/границы/offset — отказ.
- Клиент ждёт 5 с, максимум 3 отправки одного запроса. Прибор отменяет приём после
  30 с без DATA/повторного BEGIN либо при разрыве защищённого соединения. Очередь
  BLE отбрасывает команды предыдущего подключения; потеря элемента не означает ACK.
- FINISH: точный размер, `esp_ota_end`, чтение SHA-256 и product metadata из записанного
  раздела, повторная проверка подписи. Только затем проверенная запись намерения в NVS
  и `esp_ota_set_boot_partition`. Не использовать автоматически активирующий Arduino Update.
  Повтор FINISH той же выбранной операции идемпотентен.
- ABORT/ошибка до выбора слота оставляет текущую прошивку рабочей; недописанный
  неактивный слот не выбирается. Начинать следующую передачу с нуля. После выбора
  ABORT запрещён: результат устанавливается следующим запуском/QUERY.
- REBOOT — отдельный запрос после FINISH; ответ, пауза 500 мс, software reset только в ON.
  Bootloader/таблица/FS через BLE никогда не передаются.

## Доверие, ключ и первый запуск

Отдельный постоянный **OTA ECDSA P-256/SHA-256** ключ, public ID `a128f28662e56efc`.
Приватная часть сохранена вне git; резервный ZIP также приватен. Наличие в Library
и передача владельцу не подтверждены. [Хранение и выпуск](ota-signing.md).
Ключ APK прежний, не используется для проверки прошивки.

Подпись связывает hash/точный размер, модель/проводку/профиль, разметку/протоколы,
версию/release и минимальную версию приёмника. Прибор проверяет pinned public key,
manifest, SDK-валидность образа ESP32-S3 и точную metadata внутри образа. Fake/USB bench
не подписываются инструментом упаковки. Понижение/equal-release по BLE запрещено;
максимум принятого release хранится в NVS после VALID. Это программный счётчик,
**не eFuse anti-rollback**. Ключ не ротируется автоматически.

Secure Boot/flash encryption здесь **не включены**. Это проверка происхождения OTA
доверенной работающей прошивкой, а не защита от физической перепрошивки по USB или
компрометации самой текущей прошивки. Подпись APK не меняет этой границы.

Фактически используемые Arduino 2.0.17 / ESP-IDF 4.4.7 и bootloader поддерживают rollback.
Теперь C-hook `verifyRollbackLater()` переопределён и возвращает true: Arduino больше
не подтверждает образ до setup. Проверены символ/машинный код итогового ELF и совпадение
загрузчика со штатным ELF; реальный возврат на V2 пока не испытывался.

При PENDING_VERIFY включается watchdog 30 с; отказ включения блокирует подтверждение
и запрашивает откат. После завершения setup и не ранее 3 с
от начала приложения: проверка валидности сессии NVS, software HOLD/ON, профиля/разметки,
хеша работающего образа, сохранённого OTA-намерения и NVS write/read. Успех вызывает
`esp_ota_mark_app_valid_cancel_rollback`, затем сохраняется release; ошибка счётчика
не выставляет флаг подтверждённого результата клиенту. GPS-фикс, телефон и интернет
не требуются. Это **короткая базовая самопроверка**, не тест всех датчиков/LCD/SD/BLE
и не измерение EN. Зависание до подтверждения → watchdog/reset; незавершённая проверка
за 30 с → mark-invalid/reboot. Отсутствие второй базы при первом USB — отдельное ограничение.

Только сохранённые версия + полный SHA-256 + флаг здорового подтверждённого запуска
составляют успех Android. Версия app descriptor SDK не считается версией продукта.
До VALID приложение показывает проверку; при старой версии — «не подтверждено/возможен откат».
После VALID автоматический откат поздних дефектов не обещается. A/B не спасает
повреждение bootloader/NVS/таблицы, отсутствие питания или аппаратную неисправность.
Будущие изменения данных обязаны сохранять чтение предыдущей прошивкой до VALID;
разрушающих миграций в этой задаче нет.

## Поход, питание и OFF

Конструктору: [актуальная распиновка, схема ON/OFF и проверки до PCB](hardware-v2/electrical-baseline.md).
USB ESP32/BOOT/RESET и SD доступны после открытия корпуса, USB зарядки — снаружи.

Устройство самостоятельно допускает OTA только при IDLE/ENDED, остановленной записи,
без синхронизации/очереди выгрузок/буфера CAMP, с рабочей SD, ползунком ON и известной
батареей **не менее 50% и 3,8 В**. При DATA неизвестная батарея, OFF или <3,6 В отменяют
приём; перед FINISH снова строгий допуск. Проценты по напряжению — оценка; USB сам по
себе не доказывает безопасное питание. Начальные пороги консервативны, требуют измерения
на V2; неизвестный INA219 не принимается за 100%.

Свежесть обычного STATUS проверяется до BEGIN; во время передачи подтверждения OTA
являются источником прогресса, задержка STATUS при стирании не означает обрыв.
Сон, START/RESUME/настройки/кнопочные действия блокируются на время передачи,
выбора слота и первого запуска. STATUS и измерение питания продолжаются каждую секунду;
тихий SESSION не выключает этот поток. На SD OTA-образ не пишется.

Основной [ползунок](slider-power-v2.md): GPIO3 читает вторую независимую группу,
GPIO7 через D2 удерживает EN на время сохранения. GPIO7 нужен **для задержки OFF**,
а не для жеста A+B. ON через D1 должен независимо держать EN при reset/bootloader;
это не подтверждено на купленном модуле. Ползунок не заменяет команду FINISH похода:
OFF сохраняет тот же ID в RECOVERY; следующий ON — «Продолжить / Завершить».

| Когда OFF | Реализованное поведение; что проверить на макете |
|---|---|
| ACTIVE поход, включая CAMP | Финальная точка/буфер, SD close/checkpoint, NVS RECOVERY с тем же ID, журнал; только успех снимает HOLD. Следующий ON не начинает поход автоматически |
| Приём DATA | Синхронная flash-операция заканчивается на основном task, затем abort неактивного слота, штатное сохранение. Ошибка abort/save оставляет HOLD; старая база выбрана |
| FINISH/выбор слота | OFF обслуживается после возврата синхронного вызова. До активации — старая база; после неё — сохранён новый выбор, без ложного успеха/отмены |
| SELECTED, до перезапуска | Штатное сохранение, сохранённый новый слот проверится при следующем ON; приложение показывает неподтверждённый результат |
| Первый PENDING запуск | OFF не вызывает mark-valid. Следующее включение может откатить образ; приложение заново узнаёт фактическую версию |
| VALID | Обычное сохранение/выключение; успех обновления всё равно определяется ответом прибора |

Не имитировать длительность SDK-вызова как доказанное окно удержания. GPIO7 может
сброситься при reset, поэтому независимый ON→EN обязателен. При внезапном обрыве батареи
HOLD не помогает: до FINISH старый слот сохраняется по алгоритму, после выбора действует
bootloader. Физическую устойчивость flash/otadata/SD доказывает только испытание отключением.

## Приёмка: программная и на V2

Программно в текущих 0.1.32/0.10.9: 104 native, 164 Android JVM, 12 compile-probes GPIO, 4 host power-проверки;
сборки s3/bootstrap/fake/bench; публичная проверка подписи APK-bundle; негативная упаковка
fake/bench. Подставное flash-хранилище проверяет сохранение активного слота при обрыве;
оно **не воспроизводит физическое повреждение flash/SD**. Виртуальный прибор отвечает
OTA_UNSUPPORTED, эмулятор не притворяется настоящим загрузчиком.

Обязательные испытания с тестовой SD и приватными копиями данных:

| Проверка на V2 / телефоне | Критерий приёмки |
|---|---|
| Flash_id/PSRAM/проводка, USB-bootstrap | Фактические 4MB, правильная модель, исходная разметка, две копии flash, NVS/settings/bonds/SD сохранны, базовая 0.1.29 подтверждена |
| ON/reset/bootloader/оба слота | EN/GPIO7/3,3 В стабильны по осциллограммам; самостоятельный запуск, ручной запасной путь проверен |
| Обрыв BLE на BEGIN/DATA/FINISH/REBOOT, потеря ACK | Нет ложного успеха/загрузки неполного файла; переподключение даёт факт, повтор с нуля; оба слота |
| Сворачивание/блокировка/kill/перезапуск Android, XOS | Приём прекращается, операция сохранена, после подключения запрос результата без автоматической повторной записи |
| Повреждённый/обрезанный/большой/чужой файл, ключ/модель/layout/fake | Отказ, выбор рабочей базы сохранён; тестовые подписи только на контролируемом стенде |
| Питание OFF и внезапный обрыв батареи при erase/write/end/otadata | Поэтапные повторяемые отключения; старый или проверяемый новый образ загружается; приложение не объявляет успех заранее |
| Отказный образ: crash/hang/неуспешная самопроверка | Watchdog/invalid/reset, фактический откат к прежнему VALID, узнаваемый результат в Android; проверить оба направления слотов |
| OFF во время первого запуска | Нет подтверждения ради OFF; последующий ON и откат, корректный QUERY |
| OFF посреди записи похода и CAMP | Файлы/финальная точка/тот же ID/RECOVERY; следующий ON предлагает продолжение, ошибка SD держит HOLD |
| Низкая/неизвестная батарея, USB/backfeed | Безопасный отказ до BEGIN/FINISH, нет сна/START при OTA; измерены запас и потребление |
| Настройки, bonds и походы после OTA и отката | Побайтные копии SD, контрольные параметры NVS, идентичность сессии; без потери/повторного создания походов |

Отказные образы не включены в APK владельца. Пока эти испытания не выполнены,
USB-комплект и APK — **комплект для проверки**, не аппаратно принятый выпуск.

### Как отличить реальный rollback: предложение для отдельной стендовой задачи

12.11.2026, анализ основной ветки `77c978f` (0.1.32/wiring2).
**Это контракт будущих проверочных сборок: они ещё не реализованы/не собраны.**
Аппаратная E10 остаётся открытой, код владельца и APK в этой задаче не менялись.

**Подтверждено сейчас:** Arduino2.0.17/IDF4.4.7, выбранный qio_qspi SDK:
`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=1`, `CONFIG_BOOTLOADER_LOG_LEVEL=0`.
Приложение откладывает ранний VALID через `verifyRollbackLater()`, вооружает watchdog
для PENDING и имеет mark-invalid по тайм-ауту. Это возможности программной базы,
не результат аппаратного испытания. Загрузчик не печатает диагностический журнал,
на который можно полагаться как на USB-признак отката.

В USB сейчас есть баннер `vabuGEOde <version>` и при открытом Serial — журнал
версии/причины reset. **Нет** `ota status` в консоли, печати running/boot partition,
полного app-only SHA-256 и состояний обоих OTA-разделов. USB reset сам по себе
не доказывает откат. BLE QUERY сообщает фактический образ/версию/подтверждение,
но для стенда дополнительно нужна последовательность состояний разделов.
USB `ota provision` не проверяет `healthyBoot/bootFault` явно: ответ о commissioning
не заменяет чтение здорового запуска/фактического OTA-state. Допуск BEGIN отдельно
требует healthyBoot без bootFault. Этот случай учесть в диагностической базе и при
проверке полного USB-bootstrap, не объявлять зелёный commissioning аппаратной приёмкой.
Отключение SD/датчика не является надёжной инъекцией отказа: текущая короткая
boot-самопроверка их исправность не требует, хотя допуск передачи OTA требует SD/питание.

**Предложенный комплект (отдельное согласование реализации):**

| Образ / режим | Назначение и ограничения |
|---|---|
| Диагностическая рабочая база A, release N | Обычные данные/проводка wiring2, те же постоянные ключи, полноценное подтверждение VALID; при старте/после reconnect USB выводит фактические слоты/состояния/версию/hash и test/operation ID |
| TEST_FAIL_BEFORE_VALID, release >N | Успешно проходит передачу/подпись/совместимость и реально загружается в B/PENDING, затем намеренно не подтверждает самопроверку; по контролируемому тайм-ауту вызывает существующий mark-invalid/rollback |
| TEST_HANG_BEFORE_VALID, release >N | После PENDING и регистрации watchdog выводит marker и зависает до подтверждения, не кормит watchdog. Проверяется путь watchdog→bootloader→прежняя база |

Это названия **предлагаемых режимов**, не текущие PlatformIO environments/команды.
`s3_fake`/`s3_slider_bench` для них не подходят: их metadata запрещены основным OTA.
В будущем нужны отдельный профиль/упаковка с явным тестовым обозначением и защита
от попадания отказного образа в обычный APK; не ослаблять подпись, wiring/layout,
ограничения питания и прочие проверки ради теста. Версии/имена файлов назначить при
подготовке с учётом фактического high-release, не выдавать эти образы как обычный выпуск.
Для пути через существующий Android потребуется отдельный контролируемый стендовый APK
с нужным подписанным образом: выбор произвольного локального bin в обычном APK не реализован.
Приватные ключи остаются вне комплекта. Не менять eFuse, не переносить реальные походы на тестовую SD.

**Предлагаемые USB-маркеры — в 0.1.32 их ещё нет:**

```text
OTA_BOOT test=<id> running=<label/address> selected=<label/address> version=<version> sha256=<app-only hash> state=<SDK state> other_state=<SDK state> reset_reason=<reason>
OTA_TEST test=<id> mode=<fail|hang> running=<target slot> state=PENDING_VERIFY before_valid=1
```

Диагностика должна читать SDK-состояния, а не только software-флаг `healthyBoot`;
hash — тот же SHA-256 app-only байтов, что в manifest, не ELF hash из app descriptor.
Маркеры нужны **и в рабочей базе, и в отказном образе**: после отката печатает база.
USB CDC исчезает при reset, сборщик журнала должен переподключаться. Если строка
PENDING теряется, предусмотреть проверяемый след попытки, читаемый после перезапуска;
без него/снимка состояний неполный USB-журнал не считать успешной приёмкой.

**Критерий реального отката, а не обычного reset:**

1. До теста записаны известный рабочий A/VALID, его версия/hash, текущие boot/running,
   состояние B и ID попытки. Предварительно пройдена нормальная OTA-передача;
   одного первого USB с незаполненным вторым слотом недостаточно для приёмки обоих слотов.
2. Подписанный B полностью принят/выбран, есть свидетельство его реального запуска
   как PENDING_VERIFY и маркер отказа/зависания **до VALID**.
3. После reset загружен A с прежним hash/версией, фактический A — VALID;
   B — INVALID (3) после явного отказа либо ABORTED (4) после незавершённого PENDING.
   Константы соответствуют `esp_flash_partitions.h` используемого SDK.
4. Android после reconnect показывает фактически загруженный A и неподтверждённое/
   неудачное обновление, не успех B. SD/NVS/settings/bonds сравниваются до/после.
5. Контрольный обычный reset A сохраняет тот же A без новой попытки PENDING в B;
   затем повторить испытание с обратным расположением рабочего/тестового слотов.

Питание — ползунок ON, проверенное удержание EN при reset, батарея/SD и все допуски
OTA; осциллограммы питания отделяют rollback от brownout/отключения. Автоматическое
получение VALID, отсутствие второго рабочего образа, потерянные маркеры или старый
ABORTED от прошлой попытки не считать доказательством текущего отката. После VALID
эти инъекции не обещают автоматический возврат: это другое окно испытаний.

Источники: [OTA ESP-IDF 4.4.7](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/system/ota.html),
[Arduino initArduino 2.0.17](https://github.com/espressif/arduino-esp32/blob/2.0.17/cores/esp32/esp32-hal-misc.c),
[bootloader 4.4.7](https://github.com/espressif/esp-idf/blob/v4.4.7/components/bootloader_support/src/bootloader_utility.c).

## AO3401: ревизия подключения и резервный слот

Для выбранного владельцем AO3401 GPIO14 **LOW=ON/HIGH=OFF**. Это **wiring revision=2**,
отдельная от прежнего предложения HIGH=ON (revision=1, версии до 0.1.31).
Основной BLE wire=2, OTA wire=1 и layout=1 не менялись: номер проводки — другое поле.
Приложение сравнивает его, приёмник отвергает чужую ревизию до стирания слота.
Обновление wiring1 → wiring2 по BLE не предлагается; новый APK сам не меняет проводку.

Для первого макета использовать **новый комплект 0.1.32**: и USB-база 0.1.29, и
подписанный образ 0.1.32 содержат AO3401-драйвер, wiring2. Не смешивать их с прежними
комплектами 0.1.30/0.1.31. После монтажа AO3401 образ HIGH=ON будет включать свет при
программном OFF/сне; старый образ вообще без драйвера может оставить экран без света.
Старые файлы сохранены для истории, не для установки/отката на эту проводку.

OTA wiring2 использует NVS namespace `ota-v2-r2`: commissioning, transaction,
health и high-release отдельны от `ota-v2` прежней ревизии. Старые OTA-записи не
исполняются и не удаляются; настройки/походы/SD и их пространства не изменены.
Нужно новое явное `ota provision` после проверки wiring2. Номер версии один не
подтверждает правильный bootstrap: сверять комплект, SHA-256 и wiring revision.
Свободное место NVS, сохранность настроек/сопряжения и SD проверяются на макете.

Это путь **первой подготовки**, не автоматическая миграция ранее принятого прибора.
Если wiring1/OTA уже фактически установлены — сначала аудит слотов, private flash-backup,
состояния похода и high-release; не повторять bootstrap/erase-all ради смены полярности.
После первого USB есть один рабочий слот; второй заполняется проверенным OTA.
Откат и свет в обоих слотах, ON/EN при reset и сон проверяются аппаратно.
[Подключение и макетный состав](hardware-v2/electrical-baseline.md#lcd-backlight).
