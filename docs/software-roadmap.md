## 1. Основания, решения владельца и границы проверки

| Тип | Сведения |
|---|---|
| Наблюдение владельца | Приложение в целом работает, но новичку трудно понимать состояния и следующий шаг; остаются визуальные и технические недоработки |
| Наблюдение владельца | Встречаются предполагаемые ложные срабатывания GPS; устройство выключено, а приложение выглядит как продолжающийся поход без связи |
| Подтверждено владельцем | На телефоне установлен APK **0.10.1** с прежним походом. Версию прошивки ESP32 владелец не знает |
| Принятое решение | Отказ от переноса данных старой установки ради смены подписи. Специальный импорт/восстановление для этого перехода не разрабатывать |
| Последнее уточнение владельца | Переход на приложение с новым ключом планируется после существенных изменений. Удаление старого приложения и установка нового не подтверждены |
| Принятое решение | Использовать существующий новый постоянный ключ; ещё один не создавать. По словам владельца резервная копия загружена в ChatGPT Library; техническая проверка не выполнена |
| Направление для проработки | Включение устройства отдельно от явного начала похода; запуск с прибора или подключённого приложения; достоверное отображение фактического состояния |
| Требование к дальнейшему анализу | Искать реальные методы обнаружения подмены; особенно снижать необоснованное отбрасывание настоящих координат |

Новые APK/прошивки не собирались, код и поведение не менялись, испытания на телефоне,

Другие конкретные несоответствия: маячок без B_FIX отображается как «GPS выкл», хотя
приёмник может искать сигнал; GPS OFF объясняется стоянкой, хотя причиной может быть
пауза, импульсный/критический режим. «HDOP × 3 = ±метры» не является подтверждённой
оценкой ошибки или защитой от подмены. Нужна проверка смысла состояния перед правкой текста.

## 4. GPS: фактические правила и последствия

### Признаки в 0.1.19 (F5)

| Признак | Условие | Роль и риск ложного срабатывания |
|---|---|---|
| BLACKLIST | Расстояние до центра ≤ радиуса | Сильный, один отвергает точку. Настоящее посещение не отличается от подменной позиции |
| JUMP | От последней принятой точки, возраст ≤300 с: расстояние >200 м + 11 м/с × время | Сильный; не доказывает атаку. Возможны законный переезд/лодка, ошибка предыдущей опоры, восстановление после отражений. Невалидные координаты также получают JUMP |
| SNR | Не менее 5 используемых спутников с ненулевым SNR, разброс ≤3 дБ | Слабый; похожие уровни сами по себе не доказательство, сложный подменный сигнал может иметь разные уровни |
| Барометр | Калибровка включена, BME исправен, разность высот >100 м | Слабый; возможны ошибки высоты GNSS, атмосферного давления или калибровки |
| Шаги | ≥60 шагов за ≥120 с при позиции в пределах 15 м | Слабый; движение на месте, небольшой круг, ложные шаги возможны без атаки |
| PHONE | Свежесть команды ≤30 с, точность 1…1000 м; отклонение >max(3000 м, 2×точность) | Только справка с 0.1.18. Телефон не независимый эталон, его GNSS/сеть тоже ошибаются |
| TIME | Разность GPS/системных часов >300 с при доверенном времени | Только справка с 0.1.18. Ошибка часов не доказывает подмену координат |

Один сильный или два из трёх слабых дают отказ. Слабые признаки не доказаны
статистически независимыми: простое их количество не даёт вероятности атаки.
После эпизода нужны 10 с чистых согласованных фиксов, минимум три разных момента,
разрыв не более 3 с; допустимое удаление от начала восстановления — 30 + 3,5×t м.
Это ещё одно ограничение скорости: восстановление на транспорте может затягиваться.
Это вывод из условий, а не подтверждение причины конкретного похода владельца.

### Что пишется и показывается (F2/F6/A1/A3)

| Состояние | Запись и координаты | Отображение/ограничение |
|---|---|---|
| Нет свежего фикса | После 3 с без действительного фикса src=NONE; шаги/датчики продолжаются при активном походе | Поиск GPS, не подмена. Старое положение не должно считаться новым измерением |
| Грубый/начальный фикс | HDOP>5, <4 спутников или первые 5 фиксов после сброса стабилизации: src=NONE, spoof=false; координата нового фикса не сохраняется как маршрут | В STATUS fix остаётся 2D/3D; карточка может ошибочно показывать хороший сигнал |
| Принятая точка | src=GPS; запись и расстояние учитывают собственные фильтры | «Принята проверками» не означает криптографически подтверждённую позицию |
| Предполагаемая подмена | src=NONE; периодический POINT содержит spoofMask и отклонённые spoofLat/Lon, не полноценный поток всех NMEA | Красный слой, точка исключена из геометрии. Текст «координаты ложные» категоричнее имеющихся доказательств |
| Восстановление 0.1.19 | src=NONE, маска восстановления, без флага подмены и без сырых координат ожидания | APK 0.10.2 отдельно объясняет ожидание; старые записи ожидания переоцениваются при чтении, сырые данные не переписываются |
| RECORD=0 | SRC_PAUSE, датчики продолжают записываться, маршрут/километраж исключены | Это пауза, а не завершение; надпись «Выкл GPS» скрывает это различие |

В экономном runtime нет восстановления формы пути по компасу/гироскопу. Пунктир
между привязками — только связь; расстояние на участке без GPS оценивается по шагам.
Состояние питания GPS, качество фикса, подозрение и стадия похода требуют разных полей.

### Кареджи и побочные эффекты зон

Подтверждено A5 и loadBlacklist в main.cpp: центры **60.0346, 30.5693** и
**60.1161, 31.3864**, оба с радиусом **5000 м**. Второй явно подписан «Ладога, о. Кареджи».
[Публичная справочная координата острова](https://ru.wikipedia.org/wiki/Кареджи_(остров)):
60°06′59″ N, 31°22′47″ E = 60.1163889, 31.3797222. Расстояние по haversine,
R=6371000 м, до второго центра ≈**371,4 м**, то есть справочная точка находится внутри.
Это не замер всего контура острова и не доказательство настроек установленного прибора.

Законный фикс внутри действующей зоны после стабилизации получает BLACKLIST независимо
от спутников и HDOP. Приложение передаёт свои зоны при подключении; отдельно применяет
их к STATUS, старым GPS-точкам и меткам при чтении. Координаты меток скрываются,
точки становятся подозрительными; байты базы при этом сохраняются. Изменение радиуса
может менять вид истории и её расчёты. Меняется и допустимость позиции телефона.
Старый стандартный радиус 1 км мигрирует в 5 км; явный пользовательский радиус сохраняется.
Пустой сохранённый список при холодном запуске прошивки заменяется стандартными зонами.
Поэтому даже «просто отключить список» не является законченным решением.

**Предложение:** географическое совпадение использовать лишь как контекст для диагностики,
не как самостоятельное доказательство ложности. Подтверждённое владельцем желание
сохранить реальные посещения требует совместного изменения прошивки, Android и обработки
истории; точная политика пока не утверждена.

| [Wesson et al.: Power-Distortion detector](https://arxiv.org/abs/1702.06554) | Проверка мощности и формы корреляции различает отражения, подмену и глушение. Авторы сообщают об обнаружении всех атак в своих >25 наборах при <0,6% ложных тревог на отдельном канале | Нужен доступ к данным внутри GNSS-приёмника; GSV/SNR недостаточно. Этот процент не является частотой потерь наших походов; перенос результата требует испытаний |
| [Galileo/GSC: OSNMA](https://www.gsc-europa.eu/galileo/faq) | Аутентификация навигационных сообщений; GSC прямо различает аутентификацию данных и всего решения позиции/скорости/времени | Нужны совместимый приёмник, проверка времени и криптографических материалов. По текущим NMEA нельзя добавить OSNMA одним изменением ESP32. Само наличие Galileo не гарантирует аутентификацию координат |
| [UT Austin TEXBAT](https://radionavlab.ae.utexas.edu/texbat/) | Опубликованы записи реальных испытаний подмены, включая сложные сценарии ds7/ds8 | Кандидат для воспроизводимого сравнения методов; это радиоданные, а не готовые POINT. Потребуются подходящий приёмник/SDR и обработка. Здесь не воспроизводились |
| [Kartverket: Jammertest 2025](https://www.kartverket.no/om-kartverket/nyheter/alle/2025/september/rapport-fra-jammertest-2025) | Испытания оборудования при помехах и манипуляции сигналами на суше, море и в воздухе с опорными данными | Пример проверки изделия с известными условиями, а не доказательство защиты нашего модуля; рассматривать как ориентир программы испытаний |

Другие аппаратные подходы — несколько разнесённых антенн и сравнение направления прихода
или относительных фаз (есть в PNT Integrity). Они требуют нового железа, места, энергии
и проверки допущений; две близкие GPS-позиции телефона и прибора не заменяют такой метод.
Выбор нового GNSS и антенн — возможная передача конструктору после отдельного решения.

Текущий парсер получает RMC/GGA/GSA/GSV: координаты, скорость, курс, высоту, время,
HDOP, спутники/SNR. В нём нет AGC, формы корреляции, сырых псевдодальностей, фаз,
независимых решений по созвездиям или проверки OSNMA. Не утверждается, что конкретный
модуль принципиально не способен выдавать дополнительные данные: нужны точная ревизия
и документация его интерфейса. Гироскоп и постоянный компас сейчас отключены.

### Предлагаемая политика качества координат

1. Разделить «нет данных», «низкое качество», «координаты согласованы», «есть противоречие»,
   «восстановление». Слово «подмена» использовать как предположение с причиной, не установленный факт.
2. Сохранять исходные измерения и отдельно решение фильтра с версией алгоритма. Сейчас
   POINT не сохраняет все отклонённые фиксы, особенно грубые/восстановление; это требует разработки.
3. Не отвергать точку по одному географическому совпадению. При противоречии сохранять
   отдельный подозрительный сегмент, не соединять скачок и не включать его автоматически
   в достоверный километраж; предусмотреть последующий пересмотр без уничтожения исходника.
4. Проверять последовательность и неопределённость измерений, длительность разрыва,
   допустимые сценарии движения; не добавлять произвольные пороги без набора нормальных
   и подозрительных записей. Разные причины должны давать объяснимые действия.
5. Сравнивать ложные отказы, пропущенные атаки, задержку восстановления и расход энергии.
   Не заявлять «нулевые ложные срабатывания вообще»: одинаковый поток NMEA может
   соответствовать реальной и подменной позиции. Нужны дополнительные наблюдения либо
   честное состояние неопределённости.

Это не предложение выключить все проверки. Ошибочные данные сохраняются для разбора,
но сохранение не означает автоматическое признание их правильными. Конкретная политика
показа/пересмотра подозрительных сегментов — вопрос Q3 ниже.

Проверены поля/свежесть NMEA и ограничения сохранения исходных измерений.
G1–G5 деталируют S1–S3 ниже. После этого аудита владелец поручил начать: в 0.1.24

## 6. Поход: фактическая логика и предлагаемая модель

В 0.1.21 прежние автоматический старт/продолжение по 6 часам и совмещённая NEW_HIKE
заменены отдельными START/FINISH/RESUME. ID больше не переименовывается при поправке
часов. Состояние и квитанция последней операции сохраняются в NVS с проверкой чтения;
END сначала сбрасывает хвост SD. Подробный действующий контракт, кнопки и ограничения —
в [цикле похода](hike-lifecycle.md) и [протоколе](protocol.md).

Q1 реализован: холодный запуск активного похода требует «Продолжить / Завершить».
Q2 согласован, но снятие питания через HOLD/EN остаётся адаптацией V2. Ночёвка — тот
же поход с автоматическим привалом; внутренний сон не вызывает вопроса о продолжении.
Экран V1 будится любой кнопкой и гаснет через 15 секунд. Android хранит подтверждённый
END в истории, отделяет его от полноты загруженной копии, не отправляет отложенный END
после потери связи. Программные проверки пройдены; аппаратные ещё впереди.

В текущем коде до 15 точек/900 с на стоянке могут оставаться в RTC-памяти;
отключение питания теряет такой хвост. Бюджет потери Q5 не утверждён. Его необходимо
определить для дальнейшей политики периодического сброса. Штатный END уже сбрасывает
хвост, но не устраняет потерю при внезапном отключении во время активной записи.

### Что возможно до V2

Схема состояний, протокол, Android, обработка SD/повторов и анализ GPS не требуют новых
деталей. В V1 есть две кнопки и драйвер OLED; простое меню похода теперь реализовано
для исправного подключённого экрана. Его наличие у владельца не подтверждено.
Без экрана явный старт/конец доступен из нового приложения; отдельного слепого
подтверждения завершения кнопками нет.

В V2 заказан LCD GM12864-59N 128×64 ST7567/ST7567S IIC, а текущий интерфейс — OLED.
Нужны проверка экземпляра, драйвер, адреса/контраст/кнопки; меню V1 нельзя считать адаптацией V2.
DS3231/перенос MPU6050 на 0x69 и выключение питания требуют согласованного аппаратного
интерфейса. [Электрическая база](hardware-v2/electrical-baseline.md) остаётся источником
этих ограничений. Программный анализ не запускал подбор питания; позднее, 10.11.2026,
владелец поручил отдельный [подбор кнопочного выключателя](hardware-v2/button-power-selection.md).
Это исследование не утверждает аппаратный интерфейс и не запускает реализацию H1.
Позднее владелец выбрал принцип и комплект EN, затем поручил разобрать
[индикацию зарядки](hardware-v2/charging-indication.md). После отказа от сложной
обвязки и окошка выбраны два внешних LED; экранная реализация H3 отложена.

Согласование S4 можно провести до окончания сбора S1; это не разрешение параллельно запускать
реализацию. H1/H2/H3 — после аппаратных зависимостей и отдельных задач владельца.
Импорт старой установки исключён из этой очереди. Будущие экспорт/импорт/восстановление SD
могут стать отдельными задачами продукта; они не объявлены ни реализованными, ни отменёнными навсегда.

PWR0. **Программная реализация 0.1.32/0.10.9 выполнена; аппаратная приёмка впереди.**

в оба слота → матрица отказов/данные. Будущие автоматический поиск обновлений/фон/ротация
ключа не входят в этот сценарий. Размер файла сам по себе не подтверждает готовность.

## 8. Данные и программа проверки GPS

Для очередного наблюдения сначала получить INFO с версией ESP32 и версию APK.
Из доступного сейчас: общий журнал приложения/прибора, SD BIN трека/меток, текстовые
журналы с окном до и после эпизода, реальные настройки зон и режимов. Указать время и
часовой пояс, место/способ движения, включения/сон/разряд, перенос прибора, открытое
небо/помещение/метро, действия с кнопками. Различать факт наблюдения и предположение.
Новые логи не требуются для переноса старой установки: это отдельная диагностика.

Для уверенного разбора нужны синхронные входы детектора: RMC/GGA/GSA/GSV, возраст
каждого измерения, SNR используемых спутников, барометр и калибровка, шаги, обе шкалы
времени, предыдущая опорная точка, маска, стадия восстановления и итоговая запись.
Текущие логи/POINT не гарантируют весь этот набор; дополнение диагностического формата — S1,
не выполненное изменение. gps echo через USB меняет режим сна, поэтому такой опыт
нельзя автоматически переносить на обычный автономный поход.

Нормальные контрольные случаи: настоящий проход внутри/через границу зоны (либо
синтетические координаты плюс отдельный полевой опыт), открытое небо, лес, выход из
здания/метро, стоянка с движением рук, лодка/переезд, пауза и возврат, часы с ошибкой,
старый/неточный телефонный фикс, перезапуск и импульсный GPS. Атакованные — скачок,
статическая ложная точка, плавный увод, временная подмена, запись с глушением/восстановлением.
Синтетический тест не доказывает качество реального радиоприёма. Радиозаписи исследовать
через офлайн-обработку или оборудованный стенд; излучение здесь не проводится.

Эталон: известная позиция/маршрут, независимые наблюдения и данные испытательного стенда.
Второй телефон с GNSS в той же зоне помех не гарантирует независимый ответ. Эпизод с
неясной истиной размечать «не установлено». Координаты владельца не публиковать в GitHub.

Измерять отдельно: долю нормальных точек/секунд ошибочно исключённых; ложные эпизоды на
час; потерянную длину/длительность маршрута; пропуск атаки и задержку обнаружения;
время восстановления; долю неопределённых результатов; расход/потери хранения.
Набор разделить по походам и условиям на настройку и независимую проверку. Для Кареджи
критерий конкретный: география сама не отклоняет нормальную последовательность; ноль
ошибок в конечном тесте не означает нулевой риск во всех условиях. Численные общие
пороги приёмки пока не определены и должны быть согласованы до выпуска.

## 9. Решения, которые нужны от владельца

| Вопрос | Рекомендация для обсуждения | Статус |
|---|---|---|
| Q1. После внезапного перезапуска | Спросить «Продолжить / Завершить», сохранив ID и разрыв; [сценарии](hike-lifecycle.md) | Согласовано; реализовано в 0.1.21/0.10.4, аппаратная проверка впереди |
| Q2. Что делает явное полное выключение активного похода? | «Завершить текущий поход? Да/Нет»; «Нет» оставляет поход открытым и требует вопроса о продолжении при следующем включении | Согласовано владельцем; реализация зависит от питания V2 |
| Q3. Как показывать сомнительные координаты? | Сохранять отдельный помеченный сегмент, не включать автоматически в доверенный километраж; дать пересмотр после похода. География сама не доказательство | Владелец разрешил реализацию; базовая политика 2 реализована в 0.1.25/0.10.6. Пересмотр после похода и полевая приёмка отдельно |
| Q4. Нужна ли локальная отметка «Я закончил» без связи с устройством? | Допускать лишь как пользовательскую пометку; не посылать отложенный END без проверки ID и не утверждать остановку прибора | Не согласовано |
| Q5. Нужна ли пауза с записью датчиков; сколько последних данных допустимо потерять при внезапном питании? | Явно определить смысл паузы и бюджет потери; затем выбрать частоту сброса по замерам энергии/SD | Не согласовано, численные значения не выдуманы |
| Q6. Что считать существенным первым обновлением для установки? | Предлагается завершённый цикл «готов → явный старт → запись → явный конец → история», с согласованной ролью зон; объём можно сократить отдельной задачей | Не согласовано |

В 0.1.21 обычный START блокируется при недоступной SD/ошибке подготовки файлов;
временная запись только в память не выдаётся за успешное начало. Отдельный аварийный
режим с потерей данных не реализован и требует согласования.
